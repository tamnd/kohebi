# Repository, build, and distribution

`github.com/tamnd/kohebi`. A Cargo workspace.

## Crates

```
kohebi              CLI and driver for both modes
kohebi-parse        lexer, parser, AST, the `ast` module surface
kohebi-hir          lowering; the readable definition of Python semantics
kohebi-bc           register bytecode, quickening, the `dis` compatibility view
kohebi-cir          CIR definition and the shared half of its four transpilers
kohebi-core         values, shapes, collections, allocator, GC
kohebi-interp       T0
kohebi-jit          T1 and T2, deopt, OSR, code cache
kohebi-aot          whole-program analysis, sealing, Rust emission, cargo driver
kohebi-abi          the native Rust extension API and its derive macros
kohebi-pyo3-compat  the PyO3 API shim
kohebi-capi         CPython C-API emulation
kohebi-std          Rust implementations of stdlib C modules
kohebi-testing      differential harness, fuzzers, stress modes
```

Plus `pylib/`, the pure-Python standard library, mostly taken from CPython.

The dependency rule: `kohebi-core` depends on nothing else in the workspace, and everything depends on it. If that ever stops being true, something has gone wrong architecturally and it should be treated as a design bug rather than a build inconvenience.

`kohebi-hir` should be readable by someone who wants to know what Python means. That is a real requirement, not a nicety: it is where the semantics live, and a new contributor's ability to fix a compatibility bug depends on being able to find the answer in one place.

## Licensing

Worth settling before code exists, because it is expensive to change later.

**Our code:** Apache-2.0 or MIT/Apache-2.0 dual, matching Rust ecosystem convention.

**Vendored CPython stdlib.** `pylib/` will contain a substantial amount of code from CPython, which is under the PSF License Agreement. That license is permissive and compatible with redistribution, but it has attribution requirements and a specific notice that has to be preserved. Get this right from the first file, keep the provenance of every vendored module recorded, and have someone who understands licensing look at it before the first release. Being sloppy here is the kind of thing that surfaces years later at exactly the wrong moment.

**Dependencies.** Anything GPL is out, because embedding kohebi in proprietary applications is a supported use case per `08-rust-interop.md`. This matters for the `_ssl` decision specifically.

## The stencil problem

Copy-and-patch needs machine code stencils generated by LLVM at build time, per target triple. This is a real distribution problem and CPython has not solved it either; PEP 836 lists it as an unresolved blocker and defers it to PEP 774.

Three options, none good:

**Require LLVM to build.** Clean, correct, and it means `cargo install kohebi` fails for most people and every contributor needs a matching LLVM version. This is what CPython effectively does today for JIT builds.

**Ship pre-generated stencils in the crate.** Works for `cargo install`, bloats the published crate, requires a target matrix, and breaks for anyone on an unusual triple.

**Make T1 optional.** Build without LLVM and get T0 and T2 only, with a documented performance cost. Ugly, and it means the common configuration is not the tested one.

Probably: pre-generated stencils for tier-1 targets, LLVM required for anything else, T1 optional as the fallback. Decide before M4, because it affects how the stencil generator is structured.

If M0.3 concludes that TPDE is the right backend, this problem may partly disappear, which is another reason to do that evaluation early.

| Build and unit tests, Linux x86-64 / macOS ARM64 / Windows x86-64 | every push |
| CPython test suite subset | every push |
| Three-way differential harness, sampled | every push |
| Benchmarks with regression alerting | every merge to main |
| Full CPython test suite | nightly |
| All stress modes over the full suite | nightly |
| Miri over core and interop crates | nightly |
| ASan and TSan builds | nightly |
| Fuzzing | continuous |
| Top 1000 PyPI packages: install, import, test | nightly |

The nightly jobs are most of the value and most of the compute cost. Budget for them explicitly rather than discovering the bill later.

Windows deserves a note. GraalPy does not support native extensions on Windows at all. We should decide early whether Windows is a first-class target, because retrofitting it is much worse than designing for it, and a large fraction of Python users are on it.

## Distribution

Two audiences with different expectations, which means two channels.

**Python users** expect `pip install kohebi` or a standalone installer, want prebuilt binaries for their platform, and will never build from source. This is the audience that decides whether the project matters.

**Rust users** expect `cargo add kohebi` for embedding, and building from source is normal.

Both have to work well. The Python-side story is the harder one and the more important one, and it should be treated as a product problem rather than a packaging afterthought. Per `01-prior-art.md`, Pyston's lesson is that distribution friction kills runtimes that are technically fine.

The AOT mode adds a wrinkle: `kohebi build` needs a Rust toolchain on the user's machine. That is a significant barrier for a Python audience. Options are to vendor a minimal toolchain, to detect and offer to install `rustup`, or to build `kohebi build --fast` per `06-aot.md` so that the common case needs no external toolchain at all. The third is probably right.

## Wheels

Extensions must be rebuilt (`07-compatibility.md`), so there needs to be somewhere to get them from.

Following GraalPy's pattern: a patched `pip` that knows about kohebi, applies per-package compatibility patches, and pulls from a kohebi wheelhouse of prebuilt packages before falling back to building from source.

This is infrastructure, it is ongoing work rather than a one-time build, and it should be planned as such rather than discovered at M10.

## Versioning

Semantic versioning on the Rust API surface. Separately, a stated CPython language version target, so `kohebi 0.4 targets Python 3.15` is unambiguous.

Nothing is stable before 1.0, and the object model and extension ABI should be explicitly called out as unstable, because those are the two things people will build against and then be upset about.

## Documentation

Three audiences, three docs:

- **Users:** install it, run your program, what works, what does not, the divergence list from `07-compatibility.md`, and how to make things fast.
- **Extension authors:** the Rust API, the PyO3 migration guide, the threading contract.
- **Contributors:** the architecture, and specifically `kohebi-hir` as the place where Python's semantics are written down.

The compatibility page should publish the real numbers from `12-testing.md`, updated automatically, including when they are bad. Every project in this space that has been vague about compatibility has lost user trust once people discovered the truth themselves.
