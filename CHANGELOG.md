# Changelog

Patch release every few merged PRs, so there is always a recent tag to bisect from and a built binary to hand someone. A `0.x.0` when a milestone finishes.

`kohebi run` runs a program now, as long as the program stays inside what the lowering and the interpreter cover. `kohebi build` is still a stub. What exists is the workspace, the CI, the design docs, the experiments the design rests on, a frontend that reads a file and builds the tree CPython builds for it, and a tier zero interpreter that executes the bytecode compiled from it.

## Unreleased

## 0.0.17

Four merged pull requests and the release where the builtins arrive. Thirteen of them, from `abs` to `sorted`, and the piece of the machine that was in the way of the last three. `builtins` had five names in it at 0.0.16 and has eighteen now, which is most of what a program that does not import anything reaches for.

The thing worth reading is the argument checking rather than the builtins. CPython is at its least uniform there and a program can see all of it: `len` and `bool` word the same complaint two different ways, `sum` has three messages for one signature, and `sorted` reports an unknown keyword as coming from `sort()` because that is where it comes from. Every expectation in this release was read off a running 3.14.7 rather than recalled, and `kohebi-compat` grew three files that hold the whole lot byte for byte.

A builtin can call a Python function. That is one public method, `Vm::apply`, and it is the half of a call that does not care where the arguments came from. The call instruction reads its arguments out of registers and arrives there; anything written in Rust builds them itself and arrives at the same place. Until now the two halves were one function and only the instruction could reach it, which is why every builtin that wanted to run Python code was refused rather than written.

`key=` on `min`, `max` and `sorted` is the first thing through it. A key is called exactly once per element and in the order the elements arrived, which a key with a side effect can see, so it is behaviour rather than an implementation detail and there is a test that counts. `min` and `max` hold the element and its key side by side so the winner is never asked twice, and give back the element rather than the key. `sorted` takes every key up front and sorts pairs, and `reverse=True` still turns the list round after the keys are taken rather than before. A key that is not callable is complained about by the call rather than by the builtin, and on an empty iterable it is never called at all, so `sorted([], key=1)` is `[]` in the same way it is in CPython. Whatever the key raises comes straight back out with nothing about sorting wrapped round it.

The one thing worth writing down is what the split cost, because the first version of it cost something. Folding keyword arguments needs the name of the thing being called, to complain about a duplicate in that name, so the fold has to happen after the callee is resolved and cannot happen in either caller. The obvious fix, handing the unfolded keywords across as a list, put a second allocation on every keyword call and measured about nine per cent on a three million call loop. The second fix, resolving the callee into a struct the callers pass down, paid that back and cost about five per cent on positional calls instead, for passing eighty bytes across a call boundary that used to be nothing. What works is a small trait: the keyword arguments arrive as something that knows how to fold itself, the two callers have different implementations of it, and the resolution stays exactly where it was. Both paths measure level with the interpreter before the change, interleaved and taken as a minimum.

A key that never stops is caught by the recursion limit rather than by the stack, which needed checking because a key puts a builtin's Rust frames between two Python ones and that is the most stack a thousand Python calls can want.

`list`, `tuple`, `set` and `sorted`, the builtins that collect a walk. The first three are the same six lines with a different container on the end of them, and every wrong call is refused in CPython's exact words, which for these three is a different pair of messages from the pair the reducers use.

`sorted` is those six lines and a stable merge sort written out by hand. The standard library's sort was not an option for two reasons and either one alone would have been enough. A comparison here runs Python's `<` and that can raise, and a comparator returning an `Ordering` has nowhere to put the error. And `<` is the only thing Python's sort is defined in terms of, so a NaN is less than nothing and greater than nothing, which is not the total order `slice::sort_by` requires and is the kind of contract violation it is entitled to panic on. A panic is not an answer a Python program can catch.

Writing it out bought two things beyond not crashing. The sort is stable, so `sorted([1, True])` and `sorted([True, 1])` come out in the order they went in even though the two compare equal, and `reverse=True` reverses the input and the answer rather than just the answer, which is how CPython keeps that true in both directions. And the comparison order is fixed rather than whatever a library happened to do, so `sorted([1, 'a'])` and `sorted(['a', 1])` name their two operands in the same order CPython names them, which is the later element first.

`any`, `all`, `sum`, `min` and `max`, the builtins that reduce a walk to one value. All five step through the machine rather than through the iteration protocol directly, so a generator is as good an argument as a list, and all five stop as early as they are allowed to. That last part is observable rather than an optimisation: a generator with a counter in it says how far `any` walked before it found a true element, and there is a test that reads the counter.

The argument handling is again where the work is. `sum` counts its keyword arguments towards its upper limit and not towards its lower one, and words the upper complaint differently when there is nothing positional to count, which is three distinct messages for one signature. `min` and `max` read one argument as a container to walk and two or more as the candidates themselves, so `min([2, 1], [3])` is `[2, 1]` and not `1`. A tie keeps the candidate that came first, which is visible because the two can be equal without being the same object. An empty walk with no `default` is a `ValueError` naming the function, and `key=None` means no key rather than a key of `None`.

`min(key=...)` and `max(key=...)` were refused by name when these five landed, because the key is a Python function and a builtin could not call one. Splitting the call instruction into gathering arguments and invoking a callee was the one piece of work that unblocked all of them at once, and it is above.

`abs`, `repr`, `bool` and `str`. Four builtins that take one value and answer one question about it, which was the whole of what a builtin could do when they landed: a builtin was handed the machine and could not call a Python function through it, so `sorted(key=...)`, `map` and `filter` were waiting on that rather than on anyone getting round to them. These four need nothing of the sort. `abs` is the unary operators asking a fourth question of the same two number types, so it went next to them in `kohebi-core` rather than into the builtin that calls it, and `repr`, `bool` and `str` are the three things every object in the runtime already knows how to answer.

The interesting part is the argument checking, which is where CPython is least uniform and most observable. `len`, `repr` and `abs` say "takes exactly one argument (2 given)" for the wrong count while `bool` says "expected at most 1 argument, got 2", and `bool` says the first without parentheses after the name and the second with them. `str` takes its first argument by name as well as by position and complains in a third way again when given both. Each of those was read off a running 3.14.7 rather than recalled, each has a test naming which behaviour it is claiming, and the wording `len` used to write itself is now one helper that all three callers share.

`str(bytes, encoding)` is refused, because there are no codecs and there is no honest way to fake one. What is not refused is everything CPython decides before it reaches a codec: the encoding has to be a string, and it is checked before the object is checked for being decodable, which is why `str(1, 2)` complains about the 2. Those checks cost nothing to get right now and are the kind of thing a compatibility suite finds later. `str` and `bool` print as `<class 'str'>` and `<class 'bool'>` because that is what they are, even though neither is a type object here yet, and closing that gap is the same piece of work that makes `''.upper()` a lookup rather than a special case in the machine.

## 0.0.16

Five merged pull requests and the release where the object model arrives. Classes with single inheritance, methods, `__init__`, attributes on both a class and an instance, and `__qualname__` running through all of it. Generators, which suspend and resume, are their own iterator, walk under a `for` and hand what they returned to the `StopIteration` that ends them. An `assert` that raises an `AssertionError` the program cannot shadow. That is milestone one down to `with`, `match`, imports and `async`.

The pattern in all three is the same one the earlier releases found: a Python feature is usually a shape rather than a mechanism. A class body is a frame that keeps its namespace instead of throwing it away. A generator is a call that hands back its frame instead of running it. An `assert` is a branch over a raise rather than a branch into one, which is why the message is not evaluated when the test passes. None of the three needed a new idea in the interpreter loop, and the loop is the thing that has to get ten times faster later.

Every semantic decision was checked against a running CPython 3.14.7 before it was written rather than after. Which scope `class C: x = x` reads inside a function, whether a method naming a class attribute by its bare name is a `NameError`, what a generator's repr says, which of `next(g)` and `for x in g` sees the returned value, and what happens when a generator asks for its own next value. Each of those has a test that says which of the two possible answers it is claiming and why, and the compat repo now has a suite of programs kohebi can actually run held to matching CPython character for character in CI, which is the first thing in the project that fails on a difference rather than reporting one.

The generator work cost about eight percent of every call and every `for` loop in programs containing no generator at all, and the same release pays it back with interest. Calls are within two percent of where they were, the loop benchmarks are five percent past it, and three plausible explanations for the slowdown measured at exactly nothing and are written down next to the two that did not. On the i9 the whole tier zero suite now sits at 0.38x CPython on 0.56x its memory, against PyPy at 2.91x on 5.84x and GraalPy at 0.46x on 20.21x. The speed half has not started. The memory half is already ahead of every runtime in the table including CPython.

Generators. A `def` with a `yield` anywhere in it is a different kind of thing from a `def` without one, and the difference is decided when it is compiled rather than when it first suspends. Calling it runs none of the body: it binds the arguments into a frame, puts the frame in a generator object and hands that back, and the body runs a piece at a time from there. So the flag is on the body rather than on the statement, and it is in the printed HIR and in the bytecode listing where a reviewer can see it, because a body carrying it is called in a way that no listing would otherwise explain.

The frame is the whole of the state. Registers, program counter and open `try` regions all sit in it exactly as they were when the `yield` stopped, so resuming is putting the frame back on the machine and carrying on from the instruction after the one that stopped. Nothing about a generator's body is compiled differently for being in one, which is what keeps the interpreter loop the same loop, and a `yield` writes a register the way a call does because a resume hands a value back in.

The end of a generator travels as a value rather than as an exception, which is the same way this runtime already ends a walk over a list. It matters because a `for` loop and a `next` want different things from it: a loop that finishes discards whatever the generator returned, and `next` turns it into the `StopIteration` a program can see, with the returned value as the exception's argument and only the first time, since the generator is finished afterwards and a finished one is a bare `StopIteration` forever. `next(g, 'default')` swallows the whole thing including the value. Each of those was checked against a running CPython 3.14.7, along with the repr using the qualified name, a generator that raised being over, and a generator asking for its own next value being a `ValueError` rather than a deadlock.

What a generator does not have is `send`, `close` and `throw`, and `yield from`, which is written in terms of them. All four are reached as attributes of the generator object, and an attribute of anything that is not a class or an instance of one has nowhere to be looked up yet, so they are absent rather than half present. The machinery underneath them is already here: a resume carries a value in and already knows which register the last `yield` wanted it written to.

Generators cost about eight percent of every call and every `for` loop in programs that contain no generator at all, and that is paid back. Two things caused it and neither was the obvious one. The first was the loop that runs a frame: it had started returning an enum wide enough to hold a value and a register, so that a generator could learn where to resume, and a return that wide goes back through memory. Every call in the program was carrying a copy on its way out for the benefit of something only a generator reads. The register is an out parameter now, a `return` leaves it alone, and a call gives back exactly what it gave back before. The second was `for` itself, which had started asking the machine for the next value instead of stepping the container directly. That call cannot be folded into the instruction that makes it, because stepping a generator can enter a Python frame and that puts the whole thing inside the interpreter's own recursion. The container case is written out in the instruction now and only the rest goes to the machine.

The result is measured rather than assumed, on an idle machine, with the binaries alternating inside one loop so that neither of them gets the cold cache or the warm one. Calls are back to within two percent of where they were before generators existed, and the two loop benchmarks are five percent faster than that, because stepping a container in the instruction is less work than the call it replaced. Stepping a generator is two percent faster as well. Two benchmarks built from `while` loops moved by two to four percent in the other direction, and since neither contains the instruction that changed, that is where the code landed rather than what it does.

The wrong answers are worth recording too, because three plausible explanations measured at exactly nothing: the branch that checks whether a body is a generator, the reference count a frame now takes on the code it is running, and the enum that every instruction returns growing by a word. Each of those was tested by building a variant with it removed and timing that against the real thing, which is the only way to tell a cause from a story that fits.

The module's globals moved onto the machine. They used to be a local of `Vm::run` threaded down through every function that could reach an instruction, which was tighter and was also a dead end, because a builtin is handed the machine and nothing else. Anything written in Rust that has to run Python code, which is a generator being stepped by `next`, a `sorted` calling a key function and every dunder there will ever be, needs the globals that code reads. Nothing about the layout changed: a global is still one index into a dense table opened once per run, and the name table is now shared out of the module rather than borrowed from it so the slots can outlive the call that opened them.

Classes. A `class` statement runs its body, keeps the namespace the body filled, and that namespace is the class. Single inheritance, methods with `self` bound by the lookup that found them, `__init__` on construction, attributes on both a class and an instance, and set and delete on both. A class with several bases, with keyword arguments or with type parameters is still refused by name, and the first of those waits on a C3 linearization rather than on anything about classes.

A class body is not an ordinary frame and getting that right was most of the work. Its names go into a namespace rather than into slots, so a read that finds nothing there falls through to the module instead of being the `UnboundLocalError` the same read in a function would be. It is not an enclosing scope for the functions defined in it, so a method naming a class attribute by its bare name gets a `NameError` and `self.x` is how it has to be written. And a name the body binds is the body's own even where an enclosing function has one too, so `class C: x = x` inside a function reads the module's `x` and not the function's. Every one of those was checked against a running CPython 3.14.7 before it was written down, and each has a test that says which of the two answers it is claiming.

`__qualname__` came with it, because it had to. A method that is called wrongly says `C.f() takes 1 positional argument but 2 were given` rather than `f()`, a nested function reprs as `<function outer.<locals>.inner at ...>`, and a class nested in a function reprs as `<class '__main__.outer.<locals>.C'>`. All three match CPython exactly now, addresses aside, and the bare name is kept beside the qualified one because `__name__` still wants it.

What a class cannot do yet is define a dunder that the runtime calls. `__repr__`, `__eq__`, `__len__` and `__bool__` are all user code called from inside an operation that has no way to call anything, so an instance prints an address, compares by identity and is always true. Those are the right answers for a class defining none of them and the wrong ones for a class defining any, and the way in is a type object for every builtin type, which is the same thing `''.upper()` is waiting on. There is no metaclass either, which is why `class C(1)` says what actually went wrong rather than reproducing CPython's complaint about `int` taking two arguments.

`assert`, with and without a message, and the message is not evaluated when the test passes. That is the part worth stating, because `assert ok, report()` is written by somebody who expects `report` not to be called when `ok` holds. It is a branch over a raise rather than a branch into one, so everything the message needs is compiled inside the branch and a passing assertion runs a truth test and a jump.

The class it raises cannot be shadowed. A program that binds `AssertionError` to something of its own still gets a real `AssertionError` out of a failed assertion, which means the class is reached by an instruction that carries no name rather than by a global lookup. CPython separates the two the same way, with `LOAD_ASSERTION_ERROR` sitting next to `LOAD_GLOBAL` for exactly this reason. The instance still comes from the same builtin object the name finds in every program that did not shadow it, so nothing here is a second `AssertionError`.

`__debug__` is not consulted, because nothing can make it false yet. CPython throws assertions away at compile time under `-O`, and when there is a flag asking for that it goes in the lowering next to this. The other thing CPython does that this does not is warn about `assert (x, y)`, which is always true and almost always a mistake, and that belongs with the `SyntaxWarning` a `return` in a `finally` should get.

## 0.0.15

Seven merged pull requests since 0.0.14 and the release where a Python program stops being a script and starts being a program. Functions with every parameter shape the language has, closures with `nonlocal`, all three comprehensions, unpacking assignment, `raise`, `try` with all four of its clauses, and `__context__` so a mistake inside a handler prints under the exception the handler was written for. That is most of milestone one. What is left of it is classes, generators, `with`, `match` and imports.

The theme underneath those seven is that a Python feature is usually a shape rather than a mechanism. A comprehension is a function nobody had to write, so it is lowered to a `def` and a loop and gets the scoping and the captures for free. An `except` chain is a test and a body repeated, so it is lowered to ifs over one slot and the order the clauses are tried in is in the printed HIR rather than in a rule only the interpreter knows. A `finally` is compiled twice, once for the way out that worked and once for the way out that did not, which is what CPython does and means nothing has to remember what it interrupted. Every one of those decisions was made to keep the interpreter loop small, because the loop is the thing that has to get ten times faster later.

The error messages were checked against a running CPython 3.14 before they were written rather than after, and there are a lot of them: nine sentences for a call that does not match its parameters, seven for an unpacking that does not fit, four for a `nonlocal` with nothing to bind, and the whole `raise` and `except` chain printing character for character. That is worth the effort now because compatibility is a promise the project made and the cheapest time to keep it is while the code is being written.

The numbers moved and the honest reading of them got worse, which is the useful kind of change. The [tamnd/kohebi-bench](https://github.com/tamnd/kohebi-bench) suite now has a tier zero set of ten programs that run under every runtime with no startup measurement in the geomean, and on that set kohebi is 0.40x the speed of CPython at 0.56x its peak memory, against pypy at 3.01x and graalpy at 0.50x. The old 0.79x was mostly `startup` at 9.75x carrying the mean. Starting quickly is worth having and it is not what the goal is about. Two of the seven pull requests were paid for by that suite: the call path was allocating four times per call and is down to once, and the comprehension benchmark is what makes the case for inlining the three collecting comprehensions the way CPython 3.12 did.

`__context__`, so an exception raised while another one was being handled prints under it with CPython's `During handling of the above exception, another exception occurred` in between. That is a second chain rather than a longer one, because Python has two relationships here and prints a different sentence for each, and they interleave: an exception can have a cause that has a context, so the printer asks which kind a link is at every step instead of following one of them the whole way. A written `from` still wins where there is both, and writing one at all is what sets `__suppress_context__`, so `raise x from None` is how a program says that whatever it happened to be handling is nobody's business. The context is still recorded in that case and only the printing of it stops, which is also what CPython does.

What is being handled is a stack, and it belongs to the machine rather than to a frame, because a function called from an `except` clause is still inside that clause. A bare `raise` in it puts back what the clause caught, and anything else it raises records what the clause caught. That is the other half of this change: the bare `raise` that landed with `try` was resolved where it was written, so `except: raise` read the slot that clause had caught into and one written in a function called from a handler said `No active exception to reraise`. It is now resolved where it runs, and the message is left for the case it was always meant for, which is a bare `raise` with nothing being handled anywhere.

Trying the clauses is part of handling the exception rather than something that happens before it starts, so `except 5` raises its `TypeError` with the exception it was trying to catch printed above it. A `finally` that an exception reached is handling that exception too, for as long as the clause runs, which is why `try: raise ValueError finally: raise` puts the `ValueError` back. The exception leaving one of those is put back rather than raised again, which is a separate instruction and a separate HIR statement, because a `raise` a program wrote settles afresh what it was raised while handling and an exception that is only passing through must not overturn an answer already settled. CPython splits `RAISE_VARARGS` and `RERAISE` apart for the same reason.

All of it comes off again at every way out, whether that is the end of the clause, a `return`, a `break`, a `continue` or another exception. The first four replay the pop the way they already replay a `finally`, and the last is the region and the frame unwinding taking the stack back to the depth it was at when they opened, so a `finally` that raised on its way through does not leave what it was interrupting behind to be read as the context of the next thing that goes wrong. The shapes above were checked against a live CPython 3.14 and print the same thing character for character, apart from the `Traceback (most recent call last):` lines, which are waiting on a line table nothing has yet.

`try`, with all four of its clauses: `except`, `except E as e`, `except (A, B)`, a bare `except`, `else` and `finally`, nested inside each other and inside loops and functions. A clause catches its class and everything under it, so `except ArithmeticError` catches a `ZeroDivisionError`, and an exception nothing matched carries on out of the statement to whatever is outside it. `except Exception` does not catch a `KeyboardInterrupt` or a `SystemExit`, which is the hierarchy the classes below were built with finally being read by something. A clause that names something that is not an exception class raises `TypeError: catching classes that do not inherit from BaseException is not allowed`, and a tuple inside a tuple is that same mistake, because CPython used to allow one and stopped.

The exception a handler binds is the object that was raised, so `raise e` and the `except ... as e` that catches it are the same object rather than two that compare equal. One that never was an object grows one when it is caught, since a division by zero raises out of Rust and `except ZeroDivisionError as e` still has to have something to bind. `as` takes the name away again at the end of the clause, which is why an `e` left over from a handler is a `NameError` and not the exception, and the cleanup is itself a `finally` so it happens even when the handler raises.

The `except` clauses are not a list the interpreter walks. Lowering turns them into a chain of ifs over one slot, ending in a `raise` of that slot, because an `except` clause is a test and a body and the HIR already has a statement for that. The order the clauses are tried in and the fact that an unmatched exception keeps going are then in the printed HIR where they can be read, rather than in a rule the interpreter knows and nothing else does.

A `finally` runs on every way out: falling off the end, an exception, a `return`, a `break` and a `continue`. It is compiled twice, once for the way out that worked and once for the way out that did not, which is what CPython does and which means the interpreter never has to remember what it was in the middle of when the clause interrupted it. A `return` inside a `try` settles its value before the clause runs, so `try: return x finally: x = 99` returns what `x` was. A `break` or a `continue` leaving a `try` takes its regions off the handler stack and replays every `finally` it is leaving, innermost first, and a `return` written inside a `finally` replays the ones outside it and not itself.

The interpreter grew a handler stack per frame and one instruction to push one, one to pop it and one to ask whether a clause catches what is in a register. Every other instruction is still written as though nothing could go wrong: they return their failures, and the loop around them is the single place that catches one, pops a handler and jumps. A frame with nothing on its stack hands the exception to whoever called it, so a handler catching what a call three frames down raised needs no extra machinery.

`raise`, in every form it has: `raise ValueError`, `raise ValueError('boom')`, `raise e` on an instance held in a variable, and `raise x from y` with a class, an instance or `None` after the `from`. Every builtin exception class is a value a program can name, call, put in a list, return from a function or build in a comprehension, and all 66 of them are bound, from `BaseException` down to `PythonFinalizationError`. `str(e)` is the message and `repr(e)` is the call that would make it again, which is the difference between `boom` and `ValueError('boom')`, and `KeyError` is the one that prints its key the way `repr` would so that a missing key of `''` is something rather than nothing.

The classes are a hierarchy rather than a flat list, so `ZeroDivisionError` derives from `ArithmeticError` derives from `Exception` derives from `BaseException`, and `KeyboardInterrupt` and `SystemExit` deliberately do not derive from `Exception`. The `except` above is what reads it, and it was written before there was anything to read it because the alternative was a table of names that would have had to be written twice. It is one table, indented the way the tree is, and the name and the base come out of the same row so the two cannot drift apart.

A raised exception carries the object that was raised rather than only its name and its message, which is what will make `except ValueError as e` hand back the very instance a `raise e` threw. The cost of that is a pointer in the error type every operation in the runtime returns, so it is boxed: the case it pays for is a program raising something, and the case it must not slow down is division by zero.

An exception raised from another one prints the chain, oldest first, with CPython's sentence in between. What is missing between the two is the `File` and `line` pair, because there is still no line table. `raise e from e` prints once rather than forever, which is also what CPython does and for the same reason: the exception being printed counts as already printed before anything looks for its cause.

`SystemExit` is the one class that asks for something instead of reporting something, so `raise SystemExit(2)` stops with status 2 and says nothing, `raise SystemExit('no good')` prints that and fails, and a status is a byte, which is why `SystemExit(256)` is a success and `SystemExit(-1)` is the 255 a shell prints. That is what `sys.exit` will be built out of when there is a `sys`.

Two differences worth writing down. No exception has readable attributes yet, so `e.args`, `e.__cause__` and the `errno` an `OSError` is supposed to have are all kept and none of them can be read, because attribute access does not exist. And the handful of classes with a real constructor take whatever they are given here: `OSError(2, 'x')` does not set `errno` or come back as a `FileNotFoundError`, and `UnicodeDecodeError` does not demand its five arguments. Both are waiting on the attributes those arguments would be stored in.

Nothing catches any of this yet at the point this landed, so an exception leaves the program. `try` is the entry above.

Comprehensions, all three of them, so `[x * x for x in xs]`, `{x for x in xs}` and `{k: v for k, v in pairs}` work along with several `for` clauses, several conditions on each, and one comprehension nested inside another. A comprehension in Python 3 is a function you did not have to write, and that is how it is lowered here: a `def` taking one argument, a loop over it, and the container handed back. Doing it that way rather than as a loop in the frame around it is not a formality. It is what keeps the loop variable from leaking, so `[i for i in range(3)]` leaves an `i` from before it alone, and it is what makes a name read from an enclosing function a capture, which is the machinery closures already added rather than a second one that would have to agree with it.

The outermost iterable is the argument, so it is evaluated where the comprehension is written and `iter` is called there too, which is why `[x for x in 4]` raises on that line. Every clause after the first is an ordinary loop inside the frame, so its iterable is evaluated once per turn of the clause outside it, which is what makes flattening a list of lists mean what it looks like it means.

A walrus goes the other way and binds outside the comprehension, which is the rule PEP 572 settled on and the reason the pass that decides which names a frame owns had to learn to look inside one. Inside a function that means the name becomes a cell of the enclosing frame, and at module level it is a global. The two programs where that rule has no answer are `SyntaxError`s with CPython's own wording: `assignment expression cannot rebind comprehension iteration variable 'i'` and `assignment expression cannot be used in a comprehension iterable expression`.

Adding an element is an instruction rather than a lookup of `append`. The container was built by the same lowering three statements earlier, nothing else can reach it, and which of the three kinds it is was decided at the same time, so nothing has to look at what is in the register on every element and nothing a program shadows can change what happens. A dict entry reuses the item store a program would have got from `d[k] = v`, because a third instruction would have done exactly what that one already does.

CPython 3.12 stopped paying for the frame by inlining the three comprehensions that collect, keeping the scoping and dropping the call. That is an optimisation over this rather than a different meaning, and it belongs in a pass over the HIR rather than in the lowering. It is also visible in the numbers: on the new comprehension benchmark in [tamnd/kohebi-bench](https://github.com/tamnd/kohebi-bench) kohebi takes 0.24 seconds against CPython's 0.10, which is the widest gap in the suite and is a call and a cell per comprehension rather than anything about the loop inside it.

Closures, so a function defined inside a function can read and write the names around it, and `nonlocal` says which of them it means to write. A name shared that way lives in a cell that both frames hold rather than in a register in each of them, which is the difference between a closure and a copy: two functions defined in the same frame see each other's writes, a counter carries on counting between calls, and every `def` in a loop closes over the one loop variable rather than over its value at the time, so the three of them all print 3. A name captured two functions deep is carried by the function in between whether that function mentions it or not, because a capture list only reaches the frame that wrote the `def`.

Nothing that is not a closure pays for any of this. Which names need a cell is worked out while the module is compiled, from the fact that a `def` inside the body used them, so a function that captures nothing compiles to exactly what it did before cells existed and the call benchmark is unchanged.

A `nonlocal` that has nothing to bind to is now a `SyntaxError` rather than a report that the feature is missing, which meant giving the lowering a second kind of failure. All four of CPython's messages are word for word: `no binding for nonlocal 'q' found`, `nonlocal declaration not allowed at module level`, `name 'a' is parameter and nonlocal`, and `name 'x' is nonlocal and global`. A `global` in a function in between stops the search there, because from that function inwards the name really is the module's, and a `nonlocal` inside it has nothing to reach. Reading a captured name before the enclosing frame has written it, or after a `del` took it away, is `cannot access free variable 'x' where it is not associated with a value in enclosing scope`, which is a different sentence from the one an ordinary unbound local gets.

Functions, which is `def`, `lambda`, calling one, `return`, decorators, recursion and `global`. Every parameter shape Python has works and they all compose: positional, positional-only before a `/`, keyword-only after a `*`, defaults on either kind, `*args` and `**kwargs`. A parameter is a register the call fills in rather than an entry in a dictionary, so binding an ordinary call is filling a vector from zero and only a keyword argument costs a search. Defaults belong to the function object rather than to its code, which is the whole of why `def f(x=[])` shares one list between calls: the `[]` runs once, where the `def` is, and a `def` inside a loop builds a new function every turn out of the same code.

Almost all the work in a call is the ways it can go wrong. There are nine sentences Python says to a call that does not match the parameters and they are all here word for word, down to the Oxford comma in `missing 3 required positional arguments: 'a', 'b', and 'c'` and the fact that positional-only names are the one list in all of Python that is comma joined inside a single pair of quotes and printed in parameter order rather than call order. The precedence between them matters as much as the wording, because a call can be wrong in several ways at once and CPython reports keyword failures before counting failures: `f(1, 2, y=3)` on a one parameter function complains about `y` rather than about the two. Every one of the nine, plus the `UnboundLocalError` that names the variable and the `RecursionError` at the end of a runaway, was checked against a running 3.14 before it was written.

The recursion limit is 1000 and the module body counts against it the way CPython's does, so 998 nested calls work and 999 raises. A Python call is a Rust call here, which means the limit is only meaningful if the stack underneath it is big enough to reach, and the default main thread stack on Windows is one megabyte. So `kohebi run` runs the interpreter on a thread it asks for 256 MB for, rather than raising the limit or hoping. The limit is put back frame by frame on the way out, which is what makes a caught `RecursionError` leave the machine usable.

Names are one table for the whole module rather than one per body. A global has to be the same slot wherever it is read from, and a function reading `total` and the module body writing it are the same name in the same namespace, so a table per body would make them two unrelated indices and put the interpreter back to hashing a string on every global access. The namespace is opened once per run and threaded down through every call.

The call path allocates once instead of four times. A function called a million times was rebuilding its constant pool a million times, because the pool was built at the top of the interpreter loop and the loop is entered per call rather than per body. The pools are built up front now, once each, in the shape the bodies already have. The callee's name was being copied onto the heap on every call to be available to an error message that almost never happens, and is borrowed now. The arguments were collected into a vector and then moved out of it into the registers, and are read straight from the caller's frame into the callee's now, with the overflow a `*args` collects being the only case that still needs somewhere to put them. What is left is the registers themselves, which is the frame and is not going anywhere at this tier. On the new call benchmark in [tamnd/kohebi-bench](https://github.com/tamnd/kohebi-bench) that is 0.28 seconds down to 0.11 for 700,000 calls, against CPython's 0.08, where before the change calls were the one thing kohebi was clearly losing at.

Unpacking assignment, so `a, b = b, a` swaps, `a, *rest = xs` splits a container into a head and a tail, and `for key, value in pairs` walks a dict's items the way most Python does. A target nested inside another target works too, because the whole thing is one idea rather than a special case per shape: the right hand side is laid out once as a list of exactly the length the targets want, and then every target is an ordinary store reading a constant index out of that list. So `a, (b, c) = x` is that same layout twice, and a target twelve levels deep costs a line of recursion instead of a second mechanism.

Laying the value out before anything is bound is what makes the swap a swap. It is also the only way to know whether there were too many values, since an iterator does not say how long it is and being one past the end is the answer to asking for one more element and being given one. That is why the walk asks for one more than the fixed targets need, and why the count in `too many values to unpack (expected 2, got 5)` is the real length of the value rather than where the walk stopped. All seven failure messages are CPython's word for word, including the "got N" part that only 3.12 and later print, and including `cannot unpack non-iterable NoneType object` for a right hand side that was never a container in the first place. Eleven working cases and every one of those failures were checked against a running 3.14 before the code was written.

## 0.0.14

Five merged pull requests since 0.0.13 and the first release where `kohebi run` runs a Python program. Assignment, arithmetic, comparison, the boolean operators, `if`, `while`, `for`, the four container displays, subscripting, slicing, `print`, `len`, `iter`, `next` and `range`, and for a program built out of those the output is byte for byte what CPython 3.14 prints. Functions, classes, attributes, imports and `raise` are next, and a program that needs one of them stops on a `NotImplementedError` that names it rather than getting an answer nobody checked.

The first whole program numbers are in [tamnd/kohebi-bench](https://github.com/tamnd/kohebi-bench), and they are worth stating carefully. kohebi is between about a half and level with CPython on work, five to ten times faster at starting, and at about a third of its peak memory. Against a goal of 10x on 0.1x memory, memory is the half going well without anyone working on it and speed is the half that has not started, which is the intended shape at this point: this is a tier zero interpreter with no quickening, no inline caches and no assumption about what a register held last time, and it is deliberately the slowest thing the project will ever ship.

The benchmark suite earned its place twice over during this release. A new `for` loop benchmark found that the in place set operators were quadratic, and a disagreement between two machines found that the macOS CPython being measured against was built with the DTrace probes and was three times slower than a CPython should be, which had been flattering every number published from that machine. Both are fixed, and the harness now refuses to run against a baseline built that way.

The iteration protocol, so `for` loops run. Every builtin container walks: lists, tuples, strings, bytes, dicts, sets and ranges, with `break`, `continue` and the `else` clause behaving the way they do on a `while`. The end of a walk is a value rather than an exception. CPython raises `StopIteration` there, which makes every `for` loop in the language an exception handler and makes every iteration pay a little towards the one that will not happen, so here `next` writes a sentinel that the following instruction tests, and a loop compiles to an ordinary test and branch. Nothing can see the sentinel from Python, because nothing else constructs one and the only instruction that reads it is emitted immediately after the one that writes it. When generators and user defined iterators arrive they raise `StopIteration` the way Python says and the runtime turns that back into this at the boundary.

An iterator holds the container and a position rather than a copy of it, which is what CPython does and is observable in both directions: a list that grows while it is being walked keeps the walk going, and one that shrinks ends it early. A dict or a set that changes size raises `RuntimeError` instead, and the position into a dict is an index into the entry table rather than a count of live entries, so a deletion earlier in the table cannot silently shift what comes next. Strings are the one container walked from a copy, because the nth code point of UTF-8 is only reachable by counting from the front and stepping one that way would make walking a string quadratic in its length.

`range`, `len`, `iter` and `next` came with it. A range is never built, so `for i in range(1000000)` is one object and not a million, and it holds integers of any size rather than machine words, which means `range(2 ** 70, 2 ** 70 + 3)` is three numbers rather than an overflow. `len` was held back rather than shipped working on four of the six containers it should work on, and it now covers all of them plus `range`, including the corner where `len(range(2 ** 70))` is an `OverflowError` because a length has to fit in a machine word even when the range does not. A builtin also knows whether it is a function or a type, so `print(range)` says `<class 'range'>` rather than describing it as a function.

Walking a range adds the step to a running value and compares it against the stop. Computing the nth value from n instead would be a multiply and a division on every step of every counted loop in every program, and the first version did exactly that, which cost about twice what the same loop written with `while` cost. Fifty new tests cover the whole of it, checked against a running 3.14, and the `for` loop is now roughly level with CPython on the benchmark that is nothing but counting.

`s |= t` and `s -= t` update the left set in place rather than working the answer out with the ordinary operator and copying it back. Both of those only concern the members of the right hand side, and the general path was building a whole new set and then cloning it into the target, so growing a set one member at a time was quadratic: five thousand members took 0.77 seconds, ten thousand took 3.0, twenty thousand took 10.7, and a hundred thousand did not finish in any time worth waiting for. It is 0.04 seconds now. `&=` and `^=` still take the general path, because those have to look at every member of the left either way and CPython pays the same. The benchmark suite found this rather than a test did, which is the whole reason the first `for` loop benchmark was written before the first `for` loop was fast.

Subscripting and slicing, which is `x[i]`, `x[a:b:c]`, writing through either and deleting through either, on lists, tuples, strings, bytes and dicts. A slice holds three objects rather than three integers, because `x['a':'b']` builds one without complaint and only raises when a sequence tries to use it. Resolving one against a length follows CPython closely for one reason: every out of range bound in Python is quietly pulled back to the end of the sequence instead of raising, so `x[5:100]` on a list of three is empty and `x[2**100:]` is empty too rather than an `OverflowError`, while the plain index `x[2**100]` is an `IndexError` that says the number will not fit. Getting that backwards produces an exception where a program expected an empty list, which only shows up on somebody else's input. The error messages are CPython's word for word, including the places CPython is inconsistent: a `str` says its indices must be integers and does not mention slices, `bytes` calls itself "byte" in the same sentence, and item deletion says "doesn't" for a container and "does not" for something that was never one. Forty new tests cover it, half of them error paths, all checked against a running 3.14.

`list += x` now grows a list from any container rather than only from a list or a tuple. It was waiting on the iteration protocol, which it turns out not to need: every builtin container can be walked directly, nothing else can produce a value yet, and when the protocol arrives it becomes the fallback behind this rather than a replacement for it.

Arithmetic borrows its operands rather than cloning them, which is worth around 1.09x across the five end to end benchmarks and 1.33x on the one that is nothing but integer arithmetic. An operator only reads the two values it is given, and the promotion step in front of every one of them was taking them by value, so every addition in a loop copied a machine word twice and every addition on a bignum allocated twice, for two values thrown away on the next line. The promotion now hands out references, with a pair of statics standing in for the two integers a `bool` is, because an `int` here owns a boxed bignum in its large variant and so cannot be promoted to a constant. The promotion has left the profile entirely, and what sits at the top now is cloning and dropping an `Object`, which is the object representation rather than the operators and is a job for a later milestone.

Globals are a vector of slots while a body runs rather than a hash map, and on the first end to end benchmark that is the difference between 0.61x CPython's speed and roughly parity. Every name at module scope is a global, so a module that does anything in a loop reads and writes globals in that loop, and through a map each of those costs a string hash, a probe, a `memcmp` and, on a write, a fresh allocation for a key that was already in the table. The compiler had already interned every name into a dense table and the interpreter was going back to strings anyway, so now it indexes the table and none of that happens. A profile of the arithmetic benchmark before the change spent about a fifth of its time in the map and the allocator, and afterwards spends none of it there. The map is still what holds the namespace between bodies, because the name table belongs to one body and the namespace does not, and a body that raises halfway puts back what it bound before the failure.

The first numbers that compare a whole program rather than one piece of the frontend are in [tamnd/kohebi-bench](https://github.com/tamnd/kohebi-bench), on five programs written inside what the interpreter covers. Memory is the half of the goal that is going well without anyone working on it: 0.28x CPython's peak, against a target of 0.1x, which is what an enum and no per-object header buy over a `PyObject` on every value. PyPy is at around 6x the speed on 2.26x the memory, which is the trade-off worth keeping in view.

The interpreter, which is the first thing in this repository that runs a Python program. `kohebi run` reads a file, parses it, lowers it, compiles it to register bytecode and executes it, and for a program built out of assignment, arithmetic, comparison, the boolean operators, `if`, `while`, the four container displays and `print`, the output is byte for byte what CPython 3.14 prints. It is tier zero and it is meant to stay slow: no quickening, no inline caches, no assumption about what a register held last time. A tiered runtime needs one implementation nobody is optimizing, because when tier one and tier zero disagree the question is which of the two is wrong, and that question only has an answer if one of them is simple enough to read.

What the interpreter does not do yet says so rather than guessing. Attributes, iteration and `raise` each raise a `NotImplementedError` naming themselves, so a program that needs one stops on it instead of getting an answer nobody checked. The same goes for the pieces of an operator that depend on those: `list += list` and `list += tuple` are done in place and visible through every other name bound to the same list, which is what Python promises.

An escape hatch for values this object model does not know the shape of. A program needs objects that are not data, the function `print` is bound to being the first of them, and none of those can be built in `kohebi-core`: there are no classes yet, and the types the runtime needs depend on the runtime rather than on the object model, since `print` has to know where the output goes. Growing an `Object` variant for each would put all of those decisions in the wrong crate and is the sort of thing that is easy to add and hard to take back out. So there is one variant, the layer above defines the type, and this crate asks it the same handful of questions it asks any other value. Identity, equality and hashing for one are the address and are deliberately not overridable, which is what CPython says for a function too and which is what puts one in a dict and finds it again.

## 0.0.13

Six merged pull requests since 0.0.12 and a runtime value to put in the registers the bytecode names. A Python value now has a type, a truth, an identity, an equality, a hash, a repr, and the operators that work on it, and `kohebi-core` holds the integer, the string, the dict and the set they are built out of. Still nothing executes: the interpreter loop is the next piece. The parser did not change, so the numbers are where 0.0.12 left them, checked rather than assumed: the standard library is at 100.00% over 1870 files for both tokens and trees, the hand written broken corpus is at 100.00% over 122, and the mutated corpus is at 98.50% over 1200.

The operators, and an exception type to raise when they do not apply. An operator in Python is not something a value does on its own, it is a negotiation between two values, and which of the two ends up raising decides what the message says. `1 + 'a'` and `'a' + 1` are both a `TypeError` and they say different things, because in the first the integer gives up and the generic machinery writes the message, and in the second the string gets asked and writes its own. A program that prints the message can tell, so all of it is written out rather than approximated, and every string in the tests came off a running CPython 3.14. That includes the ones that changed recently: 3.14 says `division by zero` for integers where earlier versions said `integer division or modulo by zero`, and `cannot use 'list' as a set element (unhashable type: 'list')` where earlier versions said only the part in the brackets.

Arithmetic converts an integer to a float when it meets one and comparison never does, which is not an inconsistency but the only way both can be right. `2 ** 2000 + 1.0` is an `OverflowError` because there is no double that far out to add to, and `2 ** 2000 > 1e308` is `True` because you can answer that without needing one. So the comparison path truncates the float and compares against the bignum, and breaks a tie on the whole part with the sign of the fraction. Float `//` and `%` are CPython's corrected `divmod` rather than a floor of the quotient, and the correction is load bearing: it is the difference between `7.0 // 0.5` being fourteen and being thirteen, and it is what puts the sign of the divisor on a zero remainder so that `4.0 % -2.0` is `-0.0`.

Three things are missing on purpose and say so where they happen. A negative base to a fractional power is a complex number, `(-2) ** 0.5` in particular, and there is no complex type yet, so it raises rather than handing back the real part of an answer that is not real. `'%s' % x` is string formatting rather than a remainder and there is no formatter yet. And a repetition that would need more than a terabyte is refused up front as a `MemoryError`, where CPython finds out by asking the allocator, which means a request somewhere between the two gets a different answer here than there. A fixed ceiling gives every machine the same answer and keeps the process alive, and the exception is the same one either way.

The dict and the set. A dict remembers the order things were put into it, and that is a promise the language makes rather than an accident of an implementation, so it is not a thing an implementation gets to decide differently. The layout that gives it is CPython's compact dict and it is the one built here: a sparse table holding one machine word per slot, and the entries themselves packed densely in insertion order in a separate list. Iterating walks the dense list, which is why iteration is in order and why it costs a pass over the live entries rather than over a table that is mostly holes. It is also the cheaper of the two layouts, since only the sparse part is two thirds empty and a word per empty slot is a lot less than an entry per empty slot. That matters here more than in most places, because a Python program is mostly dicts and the target is a tenth of CPython's memory.

The part that is easy to get wrong and quiet when you do is deletion. A deleted slot cannot go back to being empty, because a key inserted later may have probed straight past it on the way to its own slot, and an empty there would end that probe early and lose a key that is still in the table. So a deletion leaves a tombstone, which means both the table and the entry list keep growing under churn until a resize clears them out. The two tests that matter are the ones that check the resize actually happens: ten thousand rounds of insert and delete leave a dict with eight entry slots rather than ten thousand, and a sliding window of thirty two keys over two thousand insertions keeps every key that is still in the window. There is one more for a hash that every key collides on, since that turns the table into a single long probe and is where an off by one in the walk shows itself.

`d = {1: 'a'}` then `d[True] = 'b'` leaves `1` as the key rather than `True`, which follows from the two being equal: there is nothing to update, and swapping the key would change what iterating hands back. An empty set prints `set()`, because `{}` is already an empty dict, and it is the one repr that is not the literal it came from since there is no literal for it.

Equality and hashing, which is what a dict is built out of. The rule that forces this to be exact rather than approximate is that `1 == 1.0 == True`, so all three have to hash the same and `{1: 'a'}[True]` has to find the value. CPython gets there by hashing every number of every type as its value modulo the prime 2^61-1, which agrees with itself across types by arithmetic rather than by anybody remembering to keep three cases in step, and that is why `hash(2**80)` and `hash(2.0**80)` are both 524288 without either one knowing about the other. All of it is reproduced here and every expected value in the tests came off a running CPython 3.14 rather than out of memory, including the float that has to be scaled out of the subnormal range before an exponent can be read off it and the tuple hash down to the mangled length that keeps `hash(())` where it was. Strings are the exception and have to be, since CPython seeds SipHash from the environment and `hash('a')` is a different number in two runs of the same interpreter on the same machine. Matching that is not possible and nothing may depend on it.

A dict lookup does not ask `==`, it asks `x is y or x == y`, and so does a list comparing its elements. That is not a shortcut and taking it out breaks things: `x == x` is false for a NaN, so a NaN stored in a dict would never be found again and `[nan] == [nan]` would be false where CPython says true for the same NaN in both slots. There is one place we cannot follow CPython, and it is written down where the code is rather than left to be discovered. A float is an immediate here and an object there, so two separately made NaNs are two keys in CPython and one key here. It is the same divergence as `x = 1000; y = 1000; x is y`, which the language does not promise either way, and it is the loudest case of it.

There is a runtime value now, which is the thing the interpreter will move around. It knows its type name, whether it is true, whether it is the same object as another one, and what `repr` and `str` print for it. None of that is the representation the spec asks for, which is a tagged 64-bit word over shaped heap objects, and the memory target depends on getting there. This milestone is correctness, so it is an enum with reference counted pointers in it, and the trick is that nothing outside the crate looks at a variant. Callers ask a question and get an answer, so the day the representation changes underneath them they do not.

Two details in there are worth saying out loud because they are the kind of thing that gets noticed late. A container that contains itself prints `[[...]]` rather than running off the end of the stack, which means `repr` carries the containers it is currently inside and takes them off again on the way out. Getting the second half wrong would print the same list twice in a row as a cycle, which is why there is a test for a list that holds the same sublist in both positions. And `x is x` holds for a NaN even though `x == x` does not, which is the whole reason identity is asked separately from equality rather than derived from it.

Integers have a representation you can do arithmetic on. The parser kept a big one as the decimal digits it would eventually be printed as, which was the right call when printing was the only thing this codebase did with an integer, and stops being the right call the moment something has to add two of them. So `kohebi-core` gets an `Int` that is a machine word in the common case and a bignum when it has to be. The two arms are kept normalized, so a value that fits in a word is always in the word arm whichever operation produced it, and that is what lets equality and ordering be settled without asking which arm either side is in. The spec puts small integers in the tagged word itself rather than in a heap object and that is still the plan, since this is the shape of the arithmetic rather than the shape of the storage.

The places Python and Rust disagree are written down where the code is and checked against a running CPython 3.14 rather than against memory. Division floors toward negative infinity where Rust truncates toward zero, so `-7 // 2` is `-4` and not `-3`. The remainder takes the sign of the divisor, so `-7 % 2` is `1` and `7 % -2` is `-1`, which is what makes `x % n` land inside `range(n)` for a positive `n` whatever `x` was. Both come out of one corrected `divmod` rather than from whatever the underlying type happens to do, so the word arm and the bignum arm cannot drift apart, and there is a test asserting the two pieces rebuild what they came from for every sign combination. The three operations that overflow without looking like they should, `-i64::MIN`, `i64::MIN // -1` and `abs(i64::MIN)`, each have a case of their own.

Strings and `repr` moved from `kohebi-parse` down to `kohebi-core` ahead of that. `ast.dump` prints every constant and every identifier with `repr` and that output is compared character for character against CPython, and the runtime needs the same function for the `repr` builtin. Two copies of an algorithm that has to agree down to which quote character it picked would be two things to keep in step and a divergence between them would be invisible from either side. Nothing else in the workspace changed, since `Str`, `StrBuf` and `str_repr` are re-exported from where they already were.

## 0.0.12

Three merged pull requests since 0.0.11 and the first two layers behind the frontend. A file now goes source, tree, HIR, bytecode, and `kohebi hir` and `kohebi bc` print the last two. Nothing executes any of it yet. The broken corpus goes 98.25% to 98.50%, the standard library stays at 100% over 1870 for both tokens and trees, and the hand written corpus is at 100% over 122.

The HIR compiles to register bytecode now, and `kohebi bc file.py` prints a listing of it. Register based rather than stack based, which is the choice the architecture document argues for: an instruction names the registers it reads and the one it writes, so there is no push and pop traffic to dispatch and nothing to model in the compiler, and `x = x + 1` is one instruction whose destination and left operand are the same register rather than a load, a load, an add and a store. Lua, Dalvik and YARV all made the same call. What it costs is that `co_code` and `dis` describe a stack machine we do not have, and the answer written into the spec is that the bytecode is ours and the `dis` view gets synthesized from the HIR on demand, so reading it works and rewriting `co_code` and expecting it to take effect does not. That is the first asterisk on running 100% of Python programs and it belongs in the compatibility matrix rather than being quietly true.

Nothing in the instruction set is implicit, which is the same rule the HIR follows. A conditional jump branches on a value that is already a boolean and running Python's truth protocol is its own instruction, because `__bool__` is user code and a second place for it to run is a second place for it to be wrong. A `for` loop asks for the next item and then asks whether there was one, using a sentinel no Python program can name, so the loop is an ordinary test and branch rather than an exception handler. There is one place the compiler looks at the shape of an expression rather than just compiling it: a `not` around a test gets peeled off and the jump turned around instead. That is not an optimization pass arriving early, since negating a boolean cannot run user code, so the two forms are the same program and emitting the longer one would only be noise.

The register file is the HIR's slots in the same order with scratch above them, and the scratch mark rewinds after each statement and after each finished subexpression. That is what stops a frame from growing with the length of a function rather than with its depth, so `x = (a + b) * (c + d)` needs five registers rather than seven. It does not help with nesting, and the test that says so is worth keeping: `f(g(h(1)))` really does need seven, because left to right evaluation loads each callee before evaluating its arguments and every one of them is still live at the bottom. CPython pushes exactly as much onto its stack for the same expression. Nothing is being wasted there, it is what the evaluation order costs.

Two bugs in the HIR turned up while writing the bytecode tests, which is roughly what the second layer is for. An assignment was hoisting its target's object above its value, so `a.b = c` read `a` before `c`. Python reads the value first, which is visible in `dis` and visible to any program where both names are undefined, since it is `c` that gets named in the `NameError`. The fix is that a plain assignment leaves the parts of its target as expressions and only pins them when the target itself branches, while an augmented assignment still evaluates its place once and holds it, because it reads and writes through the same place and both have to reach the same object. The other was the HIR printer dropping parentheses, so `(a + b) * (c + d)` printed as `a + b * c + d`. The HIR is a tree and has no precedence, and printing it flat was asking the reader to supply Python's rules from memory and hope they matched what the tree said.

There is a layer between the tree and the bytecode now, and `kohebi hir file.py` prints it. Its whole job is to have no hidden semantics. `a + b` is a node that names the protocol it runs rather than an opcode with rules attached somewhere else, a `for` loop is the calls to `iter` and `next` written out, and `a < b < c` is the four statements it really is, which is what makes it obvious that the middle operand is evaluated once. A question about what Python means gets one place to be answered, and the ahead of time compiler gets the structure that bytecode throws away.

One rule shapes the rest of it: an expression here cannot branch. Python has four that can, `and`, `or`, the conditional and the walrus, and every one of them lowers to statements writing a temporary. That has a consequence worth knowing about, because getting it wrong would be silent rather than loud. Operands are evaluated left to right, so an operand that emits statements can change what an operand to its left would have read, and when any operand in a group emits anything every operand in that group is pinned into a temporary first. `f(x := g())` pins `f` for exactly that reason, since the walrus could have been `f := g` and the call has to use the one that was there before.

Loops are one node rather than two. Setup runs, then the test, a false test runs the `else` clause and leaves, and `break` leaves at once and skips it. `while` needs no setup and `for` puts the call to `iter` there, which means the rule about what Python's loop `else` clause actually means is written down once instead of twice.

Functions, classes, comprehensions, `with`, `try`, `match`, imports and unpacking assignment have no lowering yet. Every one of them answers with the construct and the line it was on rather than a body with a hole in it, so `kohebi hir` on a file exits non-zero and says `line 2: a with statement is not lowered yet`. That list is the honest statement of how far this has got.

`f(x) =` with nothing after the `=` says `cannot assign to function call` now, where it used to stop at the end of the line and say `invalid syntax`. The rule CPython uses to explain a bad target asks for the targets and the last `=` and nothing after it, so a statement that runs out there is still the shape it matches. Only the first bad target is named, which is why `f(x) = a =` and `f(x) = 1 =` both blame the call, and it gets the short message even in the places where a value present would have earned the longer one about `==`. A statement whose targets are all fine, `(a) =` or `*a =`, is unaffected and is plain invalid syntax at the end of the line.

`tamnd/kohebi-compat` gained a third differential to keep this honest. Nothing is stored as an expected answer: CPython is asked at the time the comparison runs, so adding a case is adding a file, and a message CPython rewords in a future release shows up as a difference rather than as a fixture nobody updated.

## 0.0.2

The first working piece of the compiler. `kohebi-parse` turns Python source into tokens, and a new `kohebi tokenize` command prints them in the shape CPython's `tokenize` module reports.

The lexer handles the whole of Python's lexical grammar apart from f-strings: every number shape, every string prefix, implicit line joining inside brackets, explicit joining with a backslash, all three kinds of line ending, tabs and spaces with CPython's own rule for when the mix is ambiguous, form feeds, and a byte order mark. It reports errors with the wording CPython uses, because an error message is part of the language as far as anyone reading one is concerned.

`kohebi tokenize` exists so `tamnd/kohebi-compat` can diff us against CPython file by file rather than waiting for a runtime that can execute a whole program. It runs over CPython's own standard library, about 1900 files, and currently matches on 1240 of them with zero wrong answers. The other 627 are f-strings, which we refuse out loud rather than getting wrong, and they are the next piece of work.

That comparison found three bugs in a lexer that already passed 62 hand written tests. An extra DEDENT at the end of any file with more than one open block. A missing NEWLINE when the last line of a file had no line ending. Wrong positions after that point, since CPython reads such a file as though the ending were there.

Also in this release, the M0.3 sweep now has numbers from the Linux and Windows machines rather than macOS alone, and two claims published from the first run turned out to be wrong once the other platforms ran. Both are corrected in `docs/spec/`.

## 0.0.1

M0 in progress, three of its four experiments done and their results folded back into `docs/spec/`.

**M0.1, rustc on machine-generated Rust.** `kohebi build` emits Rust and shells out to `rustc`, so this had to be checked before anything got built on top of it. Gate was 60 seconds cold and 5 incremental at 10,000 Python lines. It passes at 1.9 and 0.3, and build time stays linear out to 100,000 lines, so the margin is real rather than a small-input artifact. One thing changed as a result: the emitted manifest sets `incremental = true` on a release-derived profile, because Cargo turns it off in release and without it editing one Python file rebuilds the whole crate at `opt-level = 3`. At 100,000 lines that is 17.6 seconds against 2.2. Written up in `docs/spec/06-aot.md`.

**M0.3, Cranelift versus TPDE.** T2 uses Cranelift at `opt_level=none`, with deopt state spilled to stack slots we allocate ourselves. TPDE is out for T2 because it emits ELF only on x86-64 and AArch64, so it cannot run on two of our four machines. It stays a T1 candidate on Linux.

Both configuration choices were surprises. Cranelift's optimizer is a net loss on guarded Python-shaped code, slower to compile and slower at run time from 64 operations up. And handing a guard's cold block its live values as SSA costs 5x at run time and goes quadratic at `opt_level=speed`, where routing them through a stack slot does not. So the explicit spill Cranelift's user stack maps force on us is the fast shape, not the tax it looked like. Cranelift has no deopt support and none is planned, so that layer is ours, and it sizes out comparable to the T2 compiler it serves.

**M0.4, the sealing factor.** It exists but it is 1.16x, not the 1.7x the design assumed. Unboxing is worth 22x to 116x and is where the performance actually comes from. The gate passes at 30x to 36x geomean over CPython.

M0.4 also produced the benchmarking rule the project now runs under, in `docs/spec/11-benchmarks.md`: never report a number from a single build of our own code. Two builds of identical Rust differed by 1.5x from register allocation alone, so every measurement is a median across `codegen-units` 1, 16 and 64, with the spread published next to it.

Still open in M0: how GraalPy's native extension layer works, which M10 depends on, and the M0.3 sweep on the Linux and Windows machines where `tpde-llc` can actually be built.
